# data/

由 GitHub Actions(`.github/workflows/daily-scan.yml`)自動產生,不要手動編輯。
爆量、產業流向、FOMO 在同一個 workflow 的連續步驟裡跑,順序由執行序保證。

| 路徑 | 內容 |
| --- | --- |
| `history/YYYY-MM-DD.json` | 當日上市全市場 OHLCV。`columns` 定義欄位順序,`rows` 是精簡陣列。只保留最近 30 個交易日(MA20 需要 20 天;產業流向的 rebase 圖要顯示 30 天) |
| `scans/YYYY-MM-DD.json` | 當日爆量掃描結果存查 |
| `scan-latest.json` | 最新一次掃描結果,前端讀這支 |
| `crashes/YYYY-MM-DD.json` | 當日暴跌掃描結果存查(跟爆量掃描對稱,`close < open`) |
| `crash-latest.json` | 最新一次暴跌掃描結果,前端讀這支 |
| `stock_names.json` | 代碼 → 名稱對照(直接取自 TWSE 回應)。2026-09-09 起「追蹤」分頁的新增/編輯表單也讀這支,打代號自動帶出名稱 |
| `no_trade_dates.json` | 已確認休市的日期,避免每天重複查詢 |
| `fomo-latest.json` | 最新一次 FOMO 掃描結果,前端讀這支 |
| `fomo/YYYY-MM-DD.json` | 當日 FOMO 結果存底 |
| `crash-fomo-latest.json` | 最新一次暴跌 FOMO 掃描結果,前端讀這支 |
| `crash-fomo/YYYY-MM-DD.json` | 當日暴跌 FOMO 結果存底 |
| `stock_meta.json` | 代碼 → 產業別 + 已發行普通股數(產業流向分組用) |
| `tick-latest.json` | 最新一次產業流向交叉表,前端讀這支 |
| `tick/YYYY-MM-DD.json` | 當日產業流向結果存查 |
| `tick-members-latest.json` | 各組凍結成員的逐日成交筆數(前端展開時才載入) |
| `tick-sample-members.json` | 凍結的抽樣名單。**長期狀態,不是每日產出** |
| `quotes-latest.json` | 報價快照:最新與前一日收盤價 + 30 天日報酬。持倉損益與 Kelly 的相關係數共用 |
| `risk-latest.json` | 大盤成交資訊 + 注意股 + 融資融券 + 停資停券預告 + 除權息預告,獨立分頁。今日漲跌停是前端自算,不在這份檔案裡 |
| `market-grid-latest.json` | 大盤九宮格 + 法人融資交叉分析 + 市場情緒 + 拉積盤偵測(今日快照)+ `history` 陣列(大盤 30 日追蹤表,逐日累積長到 30 天),放在籌碼/風險分頁 |
| `fx-futures-latest.json` | 匯率(央行)+ 台指期貨三大法人未平倉(FinMind),放在籌碼/風險分頁 |
| `themes.json` | 題材分類清單,**手動維護,不是排程產出**,由 Hugo 判斷資料後請 Claude Code 直接編輯這份檔案 |
| `stock-lookup-latest.json` | FOMO個股查詢:清單裡每檔的逐日開高低收量 + 融資融券 + 外資投信,前端讀這支。只留最新一份,**沒有每日存查** |
| `stock-lookup-scan-latest.json` | 爆量個股查詢:結構跟上面那份一模一樣,只是清單來源不同(見下)。只留最新一份,**沒有每日存查** |
| `stock-lookup-crashfomo-latest.json` | 暴跌FOMO個股查詢:結構同上,清單來源不同(見下)。只留最新一份,**沒有每日存查** |
| `stock-lookup-fullscan-latest.json` | 9/8全掃:結構同上,但清單是當天爆量+暴跌候選「全部」(84 檔),不是抽樣,也不是每日自動更新的一次性快照(見下) |

資料來源全部是 TWSE,免 token、免額度:

- 每日增量:OpenAPI `STOCK_DAY_ALL`(最新交易日全市場,一次呼叫)
- 補缺口:`STOCK_DAY_ALL` 是開放資料快取,收盤後不一定馬上更新
  (實測台北 19:53 時仍回傳前一交易日)。因此每天另外用按日期定址的
  `MI_INDEX` 檢查最近 5 個交易日有無缺漏,不受快取延遲影響,
  也能自動修復排程失敗漏掉的日子
- 歷史回補:`MI_INDEX?date=YYYYMMDD&type=ALL`(可指定過去日期)

資料範圍:**上市普通股**。篩選規則是代碼為四位數字且開頭非 0,因此排除
ETF(00 開頭)、權證(六位數)、特別股(如 2887A);當日無成交的個股也會剔除。

計算:`vol_ratio = 當日量 / MA20`,MA20 為 shift(1) 的前 20 個交易日均量(不含當日);
爆量條件為 `vol_ratio > 1.5` 且 `close > open` 且成交量 `>= 300,000 股(300 張)`
(`common.MIN_VOLUME_SHARES`,2026-09-09 加入,暴跌掃描共用同一個常數)。

⚠️ **絕對量下限的動機:** vol_ratio 只看「比平常放大幾倍」,一檔平常一天
只成交幾張的極薄股票,量放大 1.5 倍還是幾張,一樣會被 vol_ratio 抓進爆量/
暴跌清單。這種候選往下傳給 FOMO/暴跌FOMO 當觀察名單、又被「爆量個股
查詢」「暴跌FOMO個股查詢」隨機抽中,結果打完 FinMind 抓資料才發現
整檔都被個股查詢自己的低活躍度過濾器(`js/app.js` 的
`LOOKUP_LOW_ACTIVITY_VOLUME_LOTS`)濾掉——資料都抓完才知道沒用,額度
白花。門檻在源頭用同一個數字(300 張)先擋掉,vol_ratio 排序邏輯不變,
只是候選池變乾淨。2026-09-09 套用當天資料實測:爆量掃描 34→25 檔、
暴跌掃描 84→59 檔。

## FOMO 掃描(另一條線)

與爆量掃描共用同一個 workflow,排在爆量之後的步驟執行:

- **名單來源預設是爆量掃描的結果**(`scan-latest.json` 的前 60 名,依 vol_ratio)。
  兩者在同一個 job 內依序執行,FOMO 讀到的必定是同一次剛產生的爆量清單
- 檔數有上限是因為額度:每檔要打 4 次 FinMind,未註冊 300 次/小時、
  註冊 600 次/小時。爆量清單常近百檔(9/1 是 99 檔,全打要 400 次會爆掉)。
  前 60 名 = 60×4 + 4 次 preflight = **244 次**,未註冊模式下還在額度內,
  但只剩 56 次餘裕 —— 同一小時內重跑第二次就會撞牆。設了 `FINMIND_TOKEN`
  額度會變成 600,才有空間再往上加。抓失敗的個股會被跳過並記進 `failures`,
  不會讓整批作廢
- `watchlist.json`(repo 根目錄)是手動備援,讀不到掃描結果時會自動改用它;
  也可以手動指定 `--source watchlist`
- 資料來自 FinMind 四個 dataset:價量、融資融券、三大法人、PER/PBR
- 另外打一次 TWSE T86(全市場個股法人買賣超)算「佔全市場買超」的分母。
  分母用「買超個股加總」而非市場買賣差額 —— 差額可能是負數
  (實測 2026-08-31 外資淨賣超 143 億),當分母算出的百分比沒有意義
- 法人類別以 FinMind 的 name 欄位區分,實測只有五種:Foreign_Investor、
  Investment_Trust、Foreign_Dealer_Self、Dealer_self、Dealer_Hedging。
  外資取 Foreign_Investor(不含外資自營商),與 T86 的外資定義一致
- 金額為「淨買賣超股數 × 當日收盤價」的推估值,連續期間逐日累加。
  dataset 沒有金額欄位,顯示時一律標「約」
- 輸出檔的 `market_totals` 記錄當日全市場買超/賣超總額(股數),
  就是各檔「佔全市場」百分比的分母,可用來事後核算
- Token 由 GitHub Secret `FINMIND_TOKEN` 注入 runner,**不會進入任何靜態檔案**
- 門檻常數集中在 `scripts/fomo_score.py` 的 `THRESHOLDS`

⚠️ FOMO 用的是 `data/fomo/`,爆量掃描用的是 `data/history/`,兩者不共用路徑。

## 暴跌掃描 + 暴跌 FOMO(爆量/FOMO 的鏡射,2026-09-07 加入)

跟爆量掃描、FOMO 完全平行,同一個 workflow 裡緊接在各自後面跑
(`compute_crash.py` 接在 `compute_scan.py` 後面,`compute_crash_fomo.py`
接在 `compute_fomo.py` 後面)。

**暴跌掃描**(`compute_crash.py`):跟爆量掃描共用同一個 `vol_ratio` 門檻、
絕對量下限(300 張)與 `data/history`,唯一差別是價格條件相反 ——
`vol_ratio > 1.5` 且 `close < open`。邏輯完全對稱,`load_day()` 直接
import 自 `compute_scan.py`,不重複實作。

**暴跌 FOMO**(`compute_crash_fomo.py`):判斷一檔股票的下跌是「真跌」(法人
出貨主導,大機率續跌)還是「虛跌」(融資斷頭式恐慌錯殺,法人趁機承接,
可能是抄底機會)。抓資料、算指標的底層邏輯(FinMind 四組資料、全市場法人
買賣超、百分比計算)直接呼叫 `compute_fomo.py` 裡的函式,不重複實作,只有
名單來源(讀 `crash-latest.json` 而不是 `scan-latest.json`)與計分函式
(`fomo_score.score_stock_crash()`)不一樣。

真跌/虛跌的判斷是真漲/虛漲的**鏡射,但不是單純把號誌反過來**——這是
Hugo 跟 Claude Code 討論後定案的邏輯,寫在 `fomo_score.py` 的
`judge_real_crash()` / `judge_fake_crash()`:

| | 真漲(既有) | 真跌(鏡射) |
| --- | --- | --- |
| 必要條件 | 外資連續買超 ≥3 天 | 外資連續賣超 ≥3 天 |
| 融資 | 5 日增幅 <10%(散戶未追價) | 5 日增幅 >-10%(散戶還沒認賠減倉) |
| 券資比 | <5%(空方壓力低) | <5%(空方還沒大量進場對敲) |
| PBR | <2.0(評價未偏高) | >1.5(還沒跌到便宜) |

| | 虛漲(既有) | 虛跌(鏡射) |
| --- | --- | --- |
| 融資 | 5 日增幅 >15%(散戶追價明顯) | 5 日增幅 <-15%(疑似斷頭/恐慌認賠) |
| 外資 | 賣超或中性 | 買超或中性(趁機承接) |
| PBR | >2.5(評價偏高) | <1.2(評價已明顯偏低) |
| 成交量 | 今日量縮 | 今日量縮(賣壓漸緩) |

沒有另外發明一套「暴跌綜合分數」——虛跌分數本身就是「這波下跌像不像
散戶恐慌錯殺」的強度,直接拿來當 `crash_score`(主要排序/顯示用),
跟原本 FOMO 分數的角色一樣但沒有獨立的計分函式,因為概念上高度重疊。

「背離」(法人買賣方向分歧)沿用同一份 `judge_divergence()`,方向無關,
不用另外寫。

前端顏色刻意跟 FOMO 相反:真跌(會續跌)用危險色(紅色 `--up`),虛跌
(可能是機會)用安全色(綠色 `--down`),對應 CSS 的 `badge-crash-real` /
`badge-crash-fake`。

⚠️ 這套真跌/虛跌邏輯是這次新設計的,不是移植自 SH2 或任何驗證過的
外部公式,樣本也還沒累積,拿來當參考就好,不是驗證過的訊號。

## 個股查詢(2026-09-07 加入,2026-09-08 拆成三個分頁,2026-09-09 加第四個一次性分頁)

跟爆量/暴跌/FOMO/暴跌FOMO 平行但獨立,同一個 workflow 裡最後執行
(`fetch_stock_lookup.py`)。跟 FOMO 用的 `watchlist.json` 一樣是
**手動維護的代號清單**——這個 App 沒有後端,沒辦法讓使用者在前端即時
查任意一檔,只能「先把想深入看的代號加進清單,下次排程或手動觸發
Actions 之後才有資料」。

**前端分四個分頁,表格/標記邏輯完全相同(共用同一份 `createLookupPanel()`):**

| 分頁 | 清單來源 | 輸出 | 更新方式 |
| --- | --- | --- | --- |
| FOMO個股查詢 | `stock_lookup.json`(手動維護) | `data/stock-lookup-latest.json` | 每日排程 |
| 爆量個股查詢 | `stock_lookup_scan.json`(手動維護) | `data/stock-lookup-scan-latest.json` | 每日排程 |
| 暴跌FOMO個股查詢 | `stock_lookup_crashfomo.json`(手動維護) | `data/stock-lookup-crashfomo-latest.json` | 每日排程 |
| 9/8全掃 | 當天 `scan-latest.json`+`crash-latest.json` 候選全部(84 檔,不是抽樣) | `data/stock-lookup-fullscan-latest.json` | 一次性,手動觸發 `scan-full-candidates.yml` |

`stock_lookup.json` 最早是手動加 2313 開始的,後來加了一批從 FOMO/暴跌FOMO
候選池批次測試過的股票(見下面「量縮/量縮轉買」章節)。`stock_lookup_scan.json`
是 2026-09-08 從當天 `scan-latest.json`(爆量掃描候選,34 檔)隨機抽 20 檔
建的初始清單;`stock_lookup_crashfomo.json` 同一天從 `crash-fomo-latest.json`
(暴跌FOMO候選,60 檔)隨機抽 20 檔建的。三份都是手動維護,不會每天
重抽——想換就直接改對應的檔案。

`fetch_stock_lookup.py` 吃 `--list-file`/`--out-file` 兩個參數決定讀
哪份清單、寫到哪個輸出檔,`daily-scan.yml` 裡對三份手動維護的清單各跑
一次(共用同一支腳本、同一組欄位驗證)。`js/app.js` 用
`createLookupPanel(idPrefix, url)` 工廠函式生四個獨立的分頁實例(閉包
各自持有 loaded/data/code/openDate 等狀態),表格渲染、量縮系列標記、
標色筆記全部共用同一套程式碼,不重複。

⚠️ **額度備註:** 三份手動清單合計 61 檔 × 2 次 FinMind 呼叫 = 122 次,
加上 FOMO/暴跌FOMO 兩步(2026-09-08 實測合計約 376 次:FOMO 34 檔×4、
暴跌FOMO 60 檔×4)、產業別/匯率期貨等零星呼叫,一輪 `daily-scan.yml`
下來抓 500 次上下,600 次/小時的上限還有餘裕但不算寬。之後想再加清單
或加檔數,先看 daily-scan job 的 log 有沒有頂到上限。

### 9/8全掃(2026-09-09 加入,一次性分頁)

討論脈絡:三份手動清單各自只抽樣 20 檔,使用者發現這樣「只驗證了抽到
的那幾檔,沒驗證整個候選池」,想直接掃當天全部候選、套同一套過濾條件
把不合格的排除,再看剩下誰被標記。

跟其他三個分頁的關鍵差異是**清單來源不是手動維護的固定名單**,是當天
`data/scan-latest.json`(爆量,25 檔)+ `data/crash-latest.json`
(暴跌,59 檔)候選的**聯集**(兩者價格條件互斥,天生不重複,加總剛好
84 檔)。用 `.github/workflows/scan-full-candidates.yml`(一次性
workflow,跟 `probe-*.yml` 系列同一個「用完可留可刪」慣例)手動觸發:
inline 一段 Python 合併兩份候選代號,丟給 `fetch_stock_lookup.py`
(同一支腳本,只是清單/輸出檔換成 `/tmp/fullscan_codes.json` →
`data/stock-lookup-fullscan-latest.json`,不寫回根目錄的清單檔)。
84 檔 × 2 次 FinMind = 168 次,遠低於額度,而且是獨立觸發、不同小時
視窗,不會跟 `daily-scan.yml` 搶額度。

⚠️ **不會每天自動更新。** 這是「2026-09-08 收盤那天的候選全部長怎樣」
的快照,不是每日排程的一部分——`daily-scan.yml` 不會覆寫這個檔案。
想看新的一天的融資融券/外資投信,要再手動觸發一次
`scan-full-candidates.yml`(會覆寫成新一天的候選池,重打 168 次
FinMind)。實測(2026-09-09):84 檔抓完 0 failures,套過低活躍度+
無標記兩道過濾後剩 65 檔可查,19 檔被濾掉(全部是「整檔無標記」——
今天的候選本來就是爆量/暴跌篩出來的,量本身不會太薄,低活躍度過濾
這次沒濾掉半檔)。

#### 跟後續交易日比價格(2026-09-09 同一天加,`append_fullscan_price.py`)

使用者要在同一個分頁裡直接看到「9/8 觸發的訊號,之後幾天價格實際走了
多少」,不想每次都另外跑腳本比對。融資融券/外資投信只有 FinMind 有、
重抓要額度,但**開高低收量是 TWSE 免費資料,`data/history` 每天都有**
——`scripts/append_fullscan_price.py` 純本機運算(不打任何 API):比對
`data/stock-lookup-fullscan-latest.json` 現有的 `history_range.to` 跟
`data/history` 目前最新交易日,把兩者之間缺的每一天,用
`compute_scan.load_day()` 讀出的開高低收量直接補進每檔股票的 `rows`,
融資融券/外資投信四個欄位留 `null`(沒有意義去猜,清楚寫 null 让前端
表格自然顯示「—」)。首次跑(補 9/9)結果:84 檔全部補齊,無缺漏。

⚠️ **這幾個「補的」null 欄位一開始差點讓部分股票的新一列從表格裡消失**
——`js/app.js` 的 `lookupIsLowActivity()` 原本邏輯是「外資買賣超缺漏
就當低活躍度算」(見上面「低活躍度過濾」那節),對只有法人資料抓漏的
單一格是對的,但對「整天融資融券+外資+投信三個欄位全部一起是 null」
這種**刻意不補法人資料的價格延伸列**是錯的:9/8全掃補 9/9 那天,84 檔
裡有 12 檔剛好 9/9 成交量普通(< 300 張),整列因此被低活躍度過濾吃掉,
使用者完全看不到那天的資料。修法:`lookupIsLowActivity()` 加一條例外
——`margin_balance`/`foreign_net`/`trust_net` 三個同時是 `null` 的日子
直接不套這條過濾(單一欄位缺漏還是照舊規則處理,只有「三個全部一起缺」
這個訊號足夠特殊,才判定是刻意留白而不是抓漏)。

流程建議:每天跑完 `daily-scan.yml` 之後,如果想看 9/8全掃這批股票
今天的價格表現,手動跑一次 `python scripts/append_fullscan_price.py`
(或請 Claude 代跑)就會把新的一天價量補上,不用重打 FinMind、不用等
使用者手動觸發 workflow。

每檔股票組一張最近 N 個交易日(受 `data/history` 的 `KEEP_DAYS` 限制,
目前 30 天)的逐日大表格:

- **開高低收量**:直接用 `data/history`(TWSE,免費),不再打 FinMind。
  FinMind `TaiwanStockPrice` 的開高低欄位這個專案還沒探測驗證過
  (FOMO 只驗證過 `close`/`Trading_Volume`,沒有用到開高低),與其照
  文件猜欄位名稱,不如沿用已經在用、已經驗證過的 TWSE 資料
- **融資融券餘額(含日增減)、外資/投信買賣超**:FinMind
  `TaiwanStockMarginPurchaseShortSale` / `TaiwanStockInstitutionalInvestorsBuySell`,
  跟 FOMO 用的是同一個資料源,欄位已經驗證過。抓的日曆天視窗
  (60 天)比 `data/history` 寬,合併後只留 `data/history` 涵蓋到的
  交易日,但融資/融券的「日增減」是用視窗內完整序列往前找上一筆
  有值的資料算出來的,不會因為 `data/history` 只有 30 天就讓第一列
  的增減量變成 null
- 一檔只要 2 次 FinMind 呼叫(沒有 TaiwanStockPrice、沒有 PER),
  清單維持在個位數/十位數規模,額度幾乎不會是問題

⚠️ **單位:** `stock-lookup-latest.json` 存的量、外資/投信買賣超都是「股」
(TWSE、FinMind 兩邊原始單位就是股),融資融券餘額/增減則已經是「張」
(FinMind `TaiwanStockMarginPurchaseShortSale` 原始單位)——同一張表格兩種
單位混在一起,不是筆誤。前端(`js/app.js` 的 `lookupLots()`/
`lookupSignedLots()`)只在顯示時把量、外資、投信換算成張(÷1000)方便跟
融資融券的張數對照,資料檔本身不動。表頭都加了「(張)」標示。

輸出 `data/stock-lookup-latest.json`,**只留最新一份,沒有每日存查**——
回頭看「某天的查詢清單長怎樣」沒有意義,清單只會隨手動維護慢慢變動。

### 量縮 / 量縮轉買 / 外資出貨標記(2026-09-08 加入,純前端)

`js/app.js` 的 `computeLookupShrinkDays()` + `computeLookupBreakouts()` +
`computeLookupShrinkZone()` + `computeLookupSelloffDays()`,四個都吃這台
表格既有的 volume/foreign_net/trust_net/open/close,不用新資料源、不改
`stock-lookup-latest.json` 的結構;前三個共用同一份 `lookupVolRatios()`
算出來的「量 / 近期高點」比值。討論脈絡:使用者自己手算的方法是「量縮
至少 10 天,題材一到位就會往上一波」——先確認蹲了夠久的量縮,再等進場
的那一天。2313 在 8/12~8/25(10 個交易日裡有 8 天量縮)、8/26 外資投信
同步轉買、量能放大,就是這個方法抓到的真實案例。外資出貨是同一輪討論
延伸,對照 7/30 大跌那天。

**🔽量縮(單日):** 當天「量 / 近期高點(前 10 天內最高量)」< 0.3、且前
10 天(不含當天,跟量縮比值同一份窗口)平均日振幅 ≥ 3.5% 才標,不管有
沒有接著轉買。使用者要的不只是「轉買那天才看得到」,量縮期間本身也要
能一眼看出來——但同樣要濾掉死盤,見下面「有效振幅」那段的動機。

⚠️ **有效振幅這條門檻(2026-09-08 加,晚於下面「🔔量縮轉買」條件 2 那次)
一開始只加在 🔔量縮轉買跟 🕐蓄勢觀察名單,沒加在 🔽 單日標記——使用者
盯著三個分頁的資料發現「量縮但死盤」的股票(1325/2102/9902/1441 等)
還是會冒出 🔽 標記,於是回頭把同一道門檻也補進 `computeLookupShrinkDays()`。
三個標記/名單現在共用同一個 `LOOKUP_MIN_RANGE_PCT`(3.5%),差別只在
窗口怎麼定義(🔽 用跟量縮比值同一份「前 10 天不含當天」,🔔/🕐 用「觸發日
前 10 天不含觸發日」——兩者定義其實一致,只是給誰用而已)。

⚠️ **這個門檻(0.3)跟 🔔量縮轉買用的門檻(0.6)不是同一個數字**,是
2026-09-08 用 `scripts/probe_signal_batch.py` 把整套標記套到 FOMO+暴跌FOMO
隨機 20 檔之後拆開的:0.6 這個門檻在批次測試裡命中率高達 64%(244/380
格),幾乎每檔股票、每一天都會出現,單日標記等於變成雜訊。原本想把 0.6
直接收緊到 0.4,但套回 2313 資料會讓 8/26 那個轉買訊號(這整套標記最初
的動機)直接消失。所以拆成兩個獨立常數:🔔轉買邏輯裡用來算「窗口裡有
幾天量縮」的門檻維持 0.6 不動,只有 🔽 這個純顯示用的單日標記另外收緊
到 0.3(批次測試命中率降到 27%)。改前端記得同時改 `js/app.js` 的
`LOOKUP_BREAKOUT_SHRINK_RATIO`(給 🔔,別動)跟
`LOOKUP_SHRINK_DISPLAY_RATIO`(給 🔽)兩個常數,以及 `probe_signal_batch.py`
對應的 `SHRINK_RATIO`/`SHRINK_DISPLAY_RATIO`,兩邊定義要一致。

**🔔量縮轉買(組合訊號):**

1. 觸發日前 10 個交易日裡,至少 8 天「量 / 近期高點(前 10 天內最高量)」
   < 0.6
2. 那 10 天窗口內平均日振幅((高-低)/收盤×100)≥ 3.5%
3. 觸發日當天外資、投信買賣超同步 > 0
4. 觸發日量能 ≥ 那 10 天窗口均量的 1.2 倍

窗口/門檻(10 天、8 天)照使用者手算的方法定案。**原本窗口只抓 5 天、
門檻 3 天**,套 2313 資料會多抓到一個 8/20 的假訊號(符合三條件,但隔天
8/21 就被外資翻臉倒貨、股價回落)。改成 10 天窗口、8 天門檻之後 8/20
自然被濾掉、只剩 8/26 這一天——**不是**額外加「隔天不能反轉」的過濾
規則,是窗口拉長到跟使用者手算的方法一致之後自然的結果。

**「量縮」的基準是近期高點,不是滾動均量。** 一開始想比照爆量掃描的
`vol_ratio = 量 / MA20(shift 1)` 定義,套過 MA5/10/15/20 都測不出 2313
那段量縮——均量本身會跟著量縮一起往下掉,比值壓不到門檻以下。改成跟
近期高點比才量得出「跟爆量的高點比,縮了多少」。

**條件 2(有效振幅)是把 21 檔測試名單加進個股查詢後,使用者自己盯著
表格發現的。** 他點名 2313/4576/6168/2409/3006 這幾檔「量縮的時候價錢
還是有真正在動」,其餘量縮的股票是死盤——整段期間每日高低差距都壓在
1~2% 左右,根本沒有價格發現,不值得放進觀察名單。試過的第一個假設
「振幅逐漸收窄」(K 線實體變短,像三角收斂)對不上 2313 自己的資料——
8/12~8/25 的日振幅是 2.63%→6.60%→4.18%→2.84%→2.37%→2.89%→3.91%→
5.15%→3.76%→5.75%,上下跳動,不是單調收斂。改成「窗口內平均日振幅」
才對得上:使用者點名的 5 檔量縮窗口平均振幅都在 3.6% 以上,死盤那幾檔
(1325/2102/9902/1441 等)都在 1.1~1.7% 之間,中間有清楚的落差,門檻抓
3.5%。

**🕐 目前蹲在量縮蓄勢區、還沒等到轉買(觀察名單):** `computeLookupShrinkZone()`
跟 🔔量縮轉買同一套窗口/門檻(含有效振幅這條),差別是不要求「今天」

天數、振幅夠不夠」。使用者要的其實是這個:不是回頭看哪天觸發過,是
現在就抓「已經蹲夠天數、價錢還有在動,只差題材/轉買訊號」的候選,當

會多一句 🕐 提示;`probe_signal_batch.py` 批次測試會把這類候選另外列成
第四欄。加了有效振幅這條之後,原本觀察名單裡的 1325/8473/2537(振幅都

**🔻外資出貨(單日):** 當天 `(close-open)/open ≤ -4%` 且外資買賣超 < 0

### 低活躍度過濾(2026-09-09 加入,三個分頁都套用)

跟上面幾個「參考標記」不一樣——那些是加在既有列上的 badge,這條是直接
把整天從表格裡拿掉。`js/app.js` 的 `lookupIsLowActivity(r)`:當天成交量
< `LOOKUP_LOW_ACTIVITY_VOLUME_LOTS`(300 張)**且**外資買賣超絕對值 <
`LOOKUP_LOW_ACTIVITY_FOREIGN_LOTS`(100 張)才濾掉——用「且」不是
「或」,量縮期間本來成交量就會小,只有外資也幾乎沒進出的那幾天才算真的
沒訊號可看,任一邊有量還是留著讓使用者自己判斷。

⚠️ **資料缺漏(null)當低活躍度算,不是不濾**(2026-09-09 從「不濾」
改過來)。原本想避免把「FinMind 抓不到資料」誤判成「沒活動」,兩個
欄位只要有一個是 null 就直接放行不濾;結果使用者發現 FOMO個股查詢的
1441(大東)明明其餘 28 天全部都是每天量不到 40 張的極薄股票,卻因為
8/21、9/4 剛好外資買賣超抓不到值(null),這兩天被排除在低活躍度判斷
之外,導致下面「整檔移除」那條規則永遠不成立,股票一直留在清單裡。
改成:某一項缺漏,就用另一項還有值的欄位正常判斷那天算不算低活躍度;
兩項都缺,那天直接算低活躍度。

濾掉的天數只在「資料範圍」那行的提示文字裡報數字,**沒有像使用者手動
🙈隱藏那樣可以叫回來看**——這條是資料太薄直接判定沒意義,不是使用者的
檢視偏好,兩套機制刻意分開:低活躍度過濾發生在 badge 計算(`breakoutMap`
等)跟「顯示已隱藏」機制之前,量縮/轉買/外資出貨的滾動窗口計算吃的還是
`rec.rows` 原始未過濾序列,不會因為某天被濾掉顯示就漏算量比、影響其他
天的判斷——只有最後渲染表格那一步才把這些天跳過。

**整檔移除(2026-09-09 同一天加的延伸):** 如果一檔股票**過去 30 天每一天
都符合低活躍度條件**(用同一份 `lookupIsLowActivity()` 逐天檢查,沒有
任何一天有真正活動),這檔代號直接從下拉選單移除,不是列出來但表格空白
——這種股票留著也沒東西可看。門檻刻意抓「整檔全部都是」而不是「多數天
數」:只要有任何一天資料活躍,股票還是留著選,只是那些低活躍度的個別
日子照上面那條規則不顯示。「資料範圍」那行的括號裡會多報一句「整檔低
活躍度濾掉 N 檔」。實測(2026-09-09,null 當低活躍度算之後):FOMO個股
查詢濾掉 1441/2702/9902、爆量個股查詢濾掉 1220/1456/3168、暴跌FOMO個股
查詢濾掉 1418/3150/5546/7823。

### 下拉選單疊標記摘要(2026-09-09 加入,四個分頁都有)

「代號」下拉選單原本只顯示「代號 名稱」,現在後面會疊上這檔股票整段
30 天歷史裡 🔽/🔔/🔻/🔥 觸發過的每一天,按日期先後排序串成一串 emoji
(例如「6657 華安  🔥」、「3167 大量  🔻🔽🔽🔽🔻🔻🔻🔽🔔」)——同一種
標記觸發幾次就疊幾次,不去重,不用點開每一檔就能掃過整個下拉選單找出
哪些股票有訊號、大概是哪種型態。`js/app.js` 的 `lookupSignalBadgeSummary(rec)`
純前端算,跟表格裡的 badge 共用同一份 `computeLookupBreakouts()` 等
判斷函式,不會有兩邊算出不同結果的問題。🕐蓄勢區不算進這串——那是
「現在算不算蹲好了」的即時狀態,不是某一天觸發的離散事件,已經在選到
該股票時另外用文字提示,不會漏看。

### 訊號準度統計(2026-09-09 加入,`scripts/analyze_signal_outcomes.py`)

使用者要的不是只看「今天這批訊號」,是全部訊號的整體準度/幅度統計。

## 產業/市值 Tick 聚合(產業流向)

移植自 SH2 的 8012。純觀察型:看哪個「產業 × 市值級距」今天的成交活躍度
暴增或暴減,**不產生任何進出場訊號**,也不跟爆量/FOMO 的邏輯耦合。

### 活躍度指標

SH2 用的是 Shioaji 的逐筆 tick 數。這邊沒有 tick 資料源,改用 TWSE 每日
行情的**成交筆數**(`STOCK_DAY_ALL` 的 `Transaction` /`MI_INDEX` 的
「成交筆數」)—— 同樣是「今天成交了幾次」,不是股數也不是金額,
語意上是最接近的免費替代。實測 9/1 全市場 4,234,997 筆、1,081 檔都有值。

### 分組

- **產業別**:FinMind `TaiwanStockInfo.industry_category` 原樣落地,
  **不做任何分類合併**(SH2 那邊也沒合併)。`TaiwanStockInfo` 是全市場的
  (上市 + 上櫃 + 興櫃),代碼規則分不出來,所以用 `t187ap03_L` 的公司
  清單當「哪些是上市」的權威來源,只留上市的(實測 2,535 → 1,089 檔)

  ⚠️ **已知限制:FinMind 對上市股大量使用舊的粗分類。** 實測 1,089 檔
  上市股裡有 247 檔掛在「電子工業」這個大類 —— 台積電、鴻海、聯發科、
  大立光、中華電全在裡面,而「半導體業」只有 19 檔、「光電業」21 檔、
  「化學工業」3 檔(多數化工股掛在「化學生技醫療」)。細分類幾乎只用在
  上櫃與新上市股。結果是電子權值股全部擠進同一個「電子工業 × 大型」格子,
  這一格的鑑別力很低。

  這是 FinMind 的分類本身如此,SH2 的 44 種清單裡同樣並存「電子工業」與
  各細分類 —— 差別在 SH2 涵蓋上櫃,細分類至少對上櫃有效。要改善的話,
  `t187ap03_L` 的「產業別」是 TWSE 官方數字代碼,已經一併存進
  `stock_meta.json` 的 `twse_industry_code` 欄位備用(**目前不參與分組**),
  換不換由使用者決定 —— 換掉就不再是 SH2 的分類了
- **市值**:`已發行普通股數 × 當日收盤價 / 1e8`(億元)。股數取自 TWSE
  OpenAPI `t187ap03_L`(上市公司基本資料),就是 SH2 沒有付費
  `market_value` 欄位時的免費 fallback
- **級距**:`assign_relative_tiers` —— **組內相對排名**,不是絕對門檻。
  單一產業內依市值由大到小排,`ceil(n/3)` / `ceil(2n/3)` 兩刀切成大/中/小。

  deprecated 的絕對門檻,留在程式裡對照,v2 不用

### 抽樣凍結

每組依**股票代號**排序取前 `SAMPLE_TARGET_PER_GROUP=10` 檔,不足額全取,
第一次算出來就寫進 `tick-sample-members.json` **永久凍結**。之後即使市值
變動、分層結果會不同,成員也不跟著跳 —— 序列要能前後比較就得如此。

要重抽:`python scripts/compute_tick_flow.py --refreeze`,或在 workflow
手動觸發時把 `refreeze_tick` 設成 true。**重抽會讓歷史序列不可比**。

### 聚合

- 組內每日值 = **算術平均**(不是加總、不是中位數)
- 缺值成員**排除出當日分母,不計 0**;整組當天無人有資料 → `null`
- `sample_count`(凍結組樣本數,固定)與 `reporting_count`(當天實際
  貢獻分母的成員數)分開記,避免「n=10 但只有 3 支回報」被誤讀
- `low_n_flag`:`sample_count < 10` 時為 1,前端整列變灰並標「樣本數低」

### 四種比法

公式在 `scripts/tick_indicators.py`,是 SH2 `sh2_autorollout/indicators.py`
的原樣移植(`vals` 新到舊、`vals[0]` 是今天;分母 None 或 0 整條 None;
分子分母任一 None 該格留 None、不當 0):

| 指標 | 定義 | 需要天數 |
| --- | --- | --- |
| D0-D1 | `vals[0] - vals[1]` | 2 |
| MA21 | 21 日均,窗口內缺任一天 → `null`(all-or-nothing) | 21 |
| 固定基底 w | `vals[0] / vals[w-1]`,w ∈ 20/10/5 | w |
| 滾動基底 w | `vals[0] / vals[w]`,w ∈ 20/10/5 | w+1 |

SH2 的 `WINDOWS` 已經拿掉 30(Shioaji tick 只留 28 天湊不齊),這邊沿用
20/10/5。`fixed_30`/`rolling_30` 不產生。

### 前端

`tick-latest.json` 只存**當天那一格**的各項指標值,外加每組 30 天的原始
序列(`series_raw`)。個股逐日明細是前端用同一組公式現算的 —— 為了不讓
兩份公式默默走鐘,每次載入都會把前端算出來的當日值跟後端的逐格比對,
對不上就在表格下方標紅字說明。

染色:D0-D1 以 0 為基準、rebase 以 1 為基準,高於基準紅、低於基準綠
(沿用本站「紅漲綠跌」的慣例;SH2 8012 原本是綠正紅負)。MA21 與原始
筆數是水準值恆為正,不染色。**沒有絕對值分級門檻**,純看方向。

## 報價快照(持倉損益 / Kelly 相關係數)

`quotes-latest.json` 一支檔案服務兩個前端功能:

- **持倉損益**:要最新收盤價(算市值)與前一交易日收盤價(算今日損益)
- **Kelly 的相關係數**:要日報酬序列,才能回答「拆兩筆買不同產業該怎麼算」

用欄位平行陣列而不是每檔一個物件,省掉重複的鍵名;日報酬存成基點整數
(`ret_bp`,100 = +1.00%,新到舊)。1,081 檔 × 24 天實測 131KB。基點的
四捨五入誤差是 0.005%,對相關係數的影響遠小於「只有 30 天樣本」本身的誤差
(24 天樣本的相關係數標準誤約 ±0.20)。

### Kelly 怎麼算

單筆:本金 C、部位佔比 x、停損幅度 s、目標獲利幅度 w,贏 → `C(1+x·w)`、
輸 → `C(1-x·s)`。最大化 `E[log]` 得

```
x = p/s - (1-p)/w          部位佔本金比例
f_risk = x·s = p - (1-p)/R 停損時會虧掉的本金比例,R = w/s(賠率)
```

多筆同時持有時**不是除以筆數**。常態近似下,n 個兩兩相關係數為 ρ 的部位,

```
每筆 = 單筆Kelly / (1 + (n-1)·ρ)
```

ρ=1(完全連動,等於同一筆下兩次)才是「各半」;ρ=0(完全獨立)則各自
下滿,因為一筆爆掉不影響另一筆。ρ 由 `ret_bp` 現算,兩檔以上都查得到
代號時用實測值,否則用畫面上的手動滑桿。

實測值(2026-09-01,24 天):長榮/陽明 0.75、漢翔/長榮航太 0.67、
台積電/聯發科 0.47、台積電/台泥 0.35、台積電/漢翔 0.32、台積電/中華電 0.05。

分母設下限 0.2,免得 ρ 很負時算出爆炸性的槓桿;部位合計超過本金時按比例
壓回 100%(不假設有融資)。停損夠緊時全額 Kelly 本來就會要求槓桿 ——
這不是算錯,是 Kelly 的性質。

## 題材分類(獨立分頁)

手動維護的靜態清單,**不是排程產出、沒有對應的 fetch 腳本**——Hugo 自己
判斷資料(哪家公司受惠哪個題材、純度多少),整理好之後請 Claude Code
直接編輯 `data/themes.json`,前端純顯示。跟七步驟/爆量/FOMO/產業流向/
部位/持倉/Kelly/籌碼風險都無關,不影響任何既有邏輯。

原本規劃是券商基本資料(`brokerService/brokerList`),後來使用者決定拿掉,
換成這個題材分類分頁,理由是券商資料對這個工具沒有實際使用場景,題材
分類更貼近選股用途。

**欄位**(`data/themes.json` 是物件陣列,不是包一層 `rows`):

| 欄位 | 說明 |
| --- | --- |
| `category` | 題材/分類名稱,自由文字,前端依此分組排序 |
| `stock_code` | 股票代號 |
| `company_name` | 公司名稱 |
| `market_type` | 市場別,例如「上市」「上櫃」「興櫃」—— **這裡刻意不套用
  「只做上市普通股」那條規則**,因為這份資料是 Hugo 手動整理的參考清單,
  不是爆量/FOMO/籌碼那種吃 TWSE 全市場上市資料的自動掃描管線,兩者
  用途不同,不衝突 |
| `benefit_reason` | 受惠原因,自由文字 |
| `purity_rating` | 純度評分 1~5(主觀),前端轉成星號顯示 |

沒有「今日股價」之類的即時欄位——這份資料是分類整理用,不是報價來源,
上櫃/興櫃代號也查不到 `quotes-latest.json`(那份只涵蓋上市)。

**分組顯示 + 訊號交叉比對**:每個 `category` 是一組(`<details>` 收合),
組頭收合時只顯示「今天觸發幾檔訊號」,點開才看到全部成員(代碼/名稱/
市場別/受惠原因/純度/今日訊號)—— 這是這個分頁真正的用途:不是看單一
個股,是看**哪個題材今天有成員觸發訊號**,藉此判斷題材熱度。

訊號用的是既有的 `hunterOf()`/爆量六訊號(跟「量價訊號」分頁同一套算法,
讀 `quotes-latest.json` 的 `daily_close`/`daily_volume`,純前端算,不落地
成資料檔),涵蓋①~⑥ 六種情境(爆量暴漲、量增價不動、量增暴跌、無量暴跌、
溫和漲跌),**不是**只有爆量掃描那種「vol_ratio>1.5 且 close>open」單一
方向的條件 —— 這是特地選這套而不是沿用爆量掃描清單的原因:後者抓不到
「暴跌」,六訊號可以。上櫃/興櫃成員不在 `quotes-latest.json`(只涵蓋上市)
範圍內,訊號永遠是「—」,這是預期行為不是 bug。

### 今日漲跌停 —— 沒有用 TWT84U,自己算

`exchangeReport/TWT84U`(上市個股股價升降幅度)探測結果是近 10MB、
34,128 筆(含所有權證/ETF/牛熊證),而且 Today/PreviousDay 兩組欄位跨日

```
TodayLimitUp=35.05、TodayLimitDown=28.75 —— 這兩個用 31.90×1.1/0.9 反推
確實對得上(見下方公式),但 PreviousDayLimitUp=31.85 用同樣公式反推
9/1 收盤 31.40 對不起來,懷疑牽涉盤中基準價重設的規則,沒把握就不用。
```

改成完全不呼叫這支 API,直接用既有 `quotes-latest.json` 的 close /
prev_close(持倉損益本來就在用的同一份資料)自己算,算法是台股公開的
漲跌幅度規則:

```
漲跌停價 = 昨收 × (1 ± 10%),依「結果價位所在級距」的檔位捨入
(< 10 元:0.01、10~50:0.05、50~100:0.1、100~500:0.5、500~1000:1、≥ 1000:5)
漲停無條件捨去、跌停無條件進位
```

用 3518 的真實歷史資料核對過兩次:
- 8/31 收盤 28.55 算出的漲停價 31.40,跟 9/1 實際收盤完全一致(那天真的鎖漲停)
- 9/2 收盤 31.90 算出的漲停/跌停價 35.05 / 28.75,跟 TWT84U 官方的
  TodayLimitUp/TodayLimitDown 完全一致

這個計算整個在前端(`js/app.js` 的 `limitUpPrice`/`limitDownPrice`),
不需要任何新的資料檔或 API 呼叫。**只看得到「收在漲跌停」**,盤中曾經
觸及但收盤打開的不算 —— 沒有逐筆成交資料,做不到這個。

### 注意股的已知限制

`announcement/notice` 沒有資料時回傳一筆全空欄位的 placeholder
(`Code` 是空字串),不是空陣列也不是錯誤。**沒辦法區分「今天真的沒有
注意股」跟「TWSE 還沒公布」**,兩種情況回應長得一模一樣,前端照實講出
這個限制,不假裝知道答案。

## 大盤九宮格 + 法人融資交叉分析 + 市場情緒 + 拉積盤偵測(「籌碼/風險」分頁)

使用者提供的整合規格的落地版,`scripts/compute_market_grid.py` 產生
`data/market-grid-latest.json`,前端在「籌碼/風險」分頁最上方顯示。純觀察型
疊加分析,不是 SH2 核心交易系統的一部分,不產生任何進出場訊號,跟個股獵人
九宮格是平行但獨立的功能(參數不共用 —— 大盤波動天生被市值加權壓縮,門檻
比個股窄)。

**四個輸入全部已經在現有 pipeline 抓得到,不需要新的資料源,不需要碰
FinMind,更不需要碰 SH2**(這點直接回答了規格第 8 節「上漲/下跌家數要不要
接 finmind.db」的疑問——不用,本地資料就有):

- **ΔP_idx(加權指數單日報酬率)+ 官方成交金額/漲跌家數**:
  `twse_api.market_index_by_date()`(2026-09-10 新增)。**改版前**用
  `twse_api.market_summary()`(FMTQIK,實測只回最近兩個交易日)算 ΔP_idx,
  Turnover/漲跌家數是拿 `data/history` 的個股資料自己加總近似出來的,不是
  真正的指數或官方數字。使用者看到籌碼分頁的拉積盤提示後想要一張「大盤
  30 日追蹤表」,逼我們重新 probe 過一次(`scripts/probe_market_index_history.py`,
  已刪除,結論記在這裡):`MI_INDEX?date=&type=ALL` 除了個股報價表之外,
  還有三張表沒被用到過:
  - 「OO年OO月OO日 價格指數(臺灣證券交易所)」:56 檔指數的當日收盤/漲跌,
    `指數` 欄位等於 `"發行量加權股價指數"` 的那一列就是 TAIEX。
    **只有收盤,沒有開高低**——TWSE 的日報表本來就沒公布指數的開高低,
    跟使用者確認過,大盤 30 日追蹤表的開高低欄位留空,不是這裡漏抓。
  - 「OO年OO月OO日 大盤統計資訊」:依證券類別分類的官方成交金額/股數/
    筆數,`成交統計` 欄位 `"1.一般股票"` 那列最接近「上市普通股」,拿來當
    Turnover,取代原本自算的近似值。
  - 「漲跌證券數合計」:官方漲跌家數統計,`股票` 欄位(不是 `整體市場`,
    那個含 ETF/權證等)是格式化字串 `"259(8)"`(259 家、其中 8 家漲停),
    只取家數。跟自算的近似值對過(9/10 那天:官方 259/744/69,自算
    259/753/69),上漲/持平一致,下跌差 9 家,官方數字更準,取代自算。
  這支 API 是日期可定址的(個股回補資料本來就在用同一支),所以這三個數字
  現在**可以回補過去的交易日**,不再受限於 FMTQIK 只有兩天的問題——見下面
  「大盤 30 日追蹤表」。
- **法人買賣超金額**:`twse_api.institutional_by_date()`(T86),
  `compute_fomo.py` 已經在打同一支 API,這裡獨立再打一次(T86 免費、
  無額度限制,不像 FinMind 要省配額)。用淨股數 × 當日收盤價估算金額,
  跟 FOMO 既有的估算法一致(dataset 沒有金額欄位,是「約」數)。
  **只計入外資(不含外資自營商)+ 投信,不含自營商**——跟專案裡「外資」
  既有定義一致,但嚴格來說不是規格講的完整「三大法人」,自營商淨額
  目前沒有從 T86 拆出來。T86 同樣日期可定址,**逐日回補**(用當天
  `data/history` 的收盤價估價,回補範圍受 `data/history` 保留天數限制)。
- **融資餘額與增減**:沿用 `risk-latest.json` 的 `margin` dict 逐檔加總,
  今日/前日都在同一份快照裡,不用歷史累積,**只有「今天」這格有值**——
  沒有「大盤融資總額」的歷史資料源,history 裡舊的日子這幾個欄位是 null,
  `market_total`/`margin_delta`/`cross_signal`/`sentiment_ma5` 都一樣只算
  今天,不在 `history` 陣列的每一筆裡面。

### 大盤 30 日追蹤表(2026-09-10 新增)

`data/market-grid-latest.json` 除了原本的「今日快照」欄位(前端既有的九宮格
區塊照舊讀這些,欄位名稱沒有改,只是數值來源從自算近似值換成官方數字),
新增 `history` 陣列:新到舊,每個交易日一筆
`{date, idx_close, idx_change, idx_change_pct, turnover_amount,
advancing_count, declining_count, unchanged_count, institutional_net,
delta_p_idx, rho_idx, price_state, volume_state, grid_label, breadth_ratio,
is_lajiban}`。

跟 `data/history` 一樣的「逐日累積長到 `KEEP_DAYS`(30)天」設計:每天排程
跑 `compute_market_grid.py` 會把新的一天跟舊檔案裡的 `history` 合併(同一天
以新抓到的為準),裁到 30 天,**不需要每次都回補**。想一次補滿 30 天,
手動觸發 `daily-scan.yml` 時 `market_backfill_days` 填 29(見
`scripts/compute_market_grid.py --backfill-days`)。

`volume_state`/`grid_label`(九宮格分類)需要前 20 個交易日的 Turnover 才能
判斷「量」,`history` 天數不夠 20 天時那幾天這兩個欄位是 `null`,會隨每天
排程逐日補上,不是漏算——`price_state`/`breadth_ratio`/`is_lajiban` 不需要
歷史視窗,從第一天就有值。

### 門檻常數(spec 沒給精確值的,先用預設值,之後可調)

| 常數 | 預設值 | 依據 |
| --- | --- | --- |
| `DELTA_IDX`(δ_idx) | 0.5% | spec 定案值 |
| `EPS_IDX`(ε_idx) | 12.5% | spec 給 10~15% 範圍,取中間 |
| `MARGIN_SURGE_PCT` | 2%(相對前日融資總額) | spec 只說「變化超過門檻」沒給數字,**這是本專案自訂的預設值** |
| `SENTIMENT_LOW` / `SENTIMENT_HIGH` | 300 / 600 家 | spec 明講是舊經驗值(2022 年前後),標記可調,不是精確統計推導 |
| 拉積盤門檻 | `breadth_ratio < 1`(最保守版本) | spec 明確定案,**不套用任何查無依據的百分比** |

### 法人+融資交叉矩陣

只在九宮格判定為「資金行情啟動」(指數漲 + 量增)這格時才計算與顯示,其他格
不顯示(避免資訊過載,規格明訂)。四種組合對照規格第 3 節的表格,原樣採用。

### 市場情緒溫度計 vs 拉積盤偵測

兩者共用同一組「上漲/下跌家數」原始資料,但用法不同,前端刻意分開兩個區塊
顯示,不合併成同一指標:

- 溫度計看**絕對值**(上漲家數 5 日均跟 300/600 這兩個水位比)
- 拉積盤看**比例**(當天上漲家數 / 下跌家數,跟 1 比)

### 已知限制

- 法人買賣超只有外資+投信,不含自營商(同上,T86 目前只拆出這兩個欄位)
- `MARGIN_SURGE_PCT`、`SENTIMENT_LOW/HIGH` 都是本專案先選的預設值,規格
  明講之後要讓使用者用歷史資料回測校準,不是最終定案的數字
- 這幾個 flag 都還沒經過 Gate 1 驗證(N≥60 pre-registered predictions),
  純資訊展示,不是進出場依據

## 匯率 / 期貨三大法人(「籌碼/風險」分頁)

使用者要求「查查能不能把匯率跟期貨空單加進來」,`scripts/fetch_fx_futures.py`
產生 `data/fx-futures-latest.json`,跟籌碼/風險其他區塊、大盤九宮格、題材
分類都無關,獨立一塊。第一次碰央行、期交所、FinMind 的期貨資料集,都先
寫 probe(`probe_fx_taifex.py`、`probe_finmind_futures.py`,已刪除)在
Actions 上跑過,不是照文件猜的。

**匯率**:央行 `cpx.cbc.gov.tw/api/OpenData/FTDOpenData_Day`,免 token。
實測**一次回應就是全部歷史**(2026-09-05 探測到 4642 筆,回溯到 2008
年),欄位是 `{"日期":"20080102","NTD_USD":"32.443"}`(日期西元 YYYYMMDD
字串,不是民國)。跟 TWSE 大多數「只給最新一兩天」的端點不同,不用自己
每天存歷史 —— `cbc_api.usd_twd_history()` 每次重新抓、切最近 30 天即可。

**期貨三大法人未平倉,兩個資料源探測結果**:

- **TAIFEX OpenAPI**(`openapi.taifex.com.tw/v1/...`,期交所自己的
  OpenAPI,跟 TWSE 那支不同網域):端點名稱
  `MarketDataOfMajorInstitutionalTradersDetailsOfFuturesContractsBytheDate`
  (三大法人-區分各期貨契約-依日期)探測正確,欄位也拿到了,但**只回最新
  一個交易日,沒有歷史查詢**——沿用跟 FMTQIK 一樣的限制。
- **FinMind `TaiwanFuturesInstitutionalInvestors`**:改用這支,**免費額度
  就能查、而且有歷史區間**(實測 `data_id="TX"` 查一個月拿到 25 個交易日,
  2026-08-03~09-04)。跟 `fetch_stock_meta.py`/`compute_fomo.py` 一樣的坑:
  **一定要帶 `data_id`**,不帶會回 400「Your level is free」。欄位:
  `date, futures_id, institutional_investors(自營商/投信/外資),
  long_open_interest_balance_volume(多單未平倉口數),
  short_open_interest_balance_volume(空單未平倉口數)` + 對應金額欄位。

**決定改用 FinMind、放棄 TAIFEX OpenAPI**——後者「只有最新一天」代表要另開
`data/futures/YYYY-MM-DD.json` 逐日存底才能看趨勢,FinMind 一次查詢就有
歷史,實作簡單很多,且免費額度就夠用,不用等 `FINMIND_TOKEN` 設定。

**外資淨部位** = `foreign_long_oi - foreign_short_oi`,負值是淨空單(散戶
最常看的期貨籌碼指標)。自營商/投信的原始未平倉口數也一併存進
`data/fx-futures-latest.json` 的 `futures.history`,只是前端目前只顯示
外資這條。
